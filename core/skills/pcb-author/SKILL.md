# PCB author

Personal skill, and the only write path for a board design. kicad-review stays read-only and checks what this skill produces. Project facts (which board, which firmware pin header, fab, layer count, harness pinouts) come from the repo's `CLAUDE.md` `## Hardware` section and its design notes; never guess a pin map or a part number.

## Fixed decisions

- **Fable only.** KiCad design files (`.kicad_sch`, `.kicad_pcb`, `.kicad_pro`, `.kicad_sym`, `.kicad_mod`, `.kicad_wks`, `.kicad_dru`) and Zener sources (`.zen`) are changed by Claude Fable 5.2 or later and no other model. `~/.claude/hooks/guard-kicad-edit.sh` enforces it for Edit, Write, shell writes into those files, the writing `pcb` subcommands, `kicad-cli ... upgrade`, text-to-cad's `kicad_pcb.edit` / `kicad_sch.edit` and the writing tools of any KiCad MCP server. On another model: stop and hand the work to Fable (the user switches with `/model fable`, or the orchestrator launches `general-purpose` with `model: "fable"` and `effort: "high"`). Never route around the hook with a script that writes the files.
- **Not through text-to-cad's `pcb` skill.** It is denied in settings: its `kicad_pcb.edit` runs kicode's KiCad nightly (10.99) and saves the board in the nightly's format, which `pcb import` rejects and a KiCad 10.0 release may refuse to open. Its read-only `cad kicad_pcb snapshot` and `inspect` are fine for an extra view of the board. A subagent's first tool call has no model on record and is denied: read a file first, then write.
- **Zener is the source.** A design change is an edit to a `.zen` file followed by a regenerate, never a hand edit of the generated schematic. Placement, tracks and zones live in the `.kicad_pcb`, which is persistent state that `pcb layout` syncs into rather than rewrites.
- **Hand-drawn boards are not edited in place.** A project the user drew in the KiCad GUI is brought in with `pcb import` into a new directory and worked on there. The original file is changed only when the user asks, in this conversation, for that named file to be changed.
- **Checkpoint before every step that writes.** `git status` clean for the board directory, or a copy next to it, so a failed import or a bad sync is one `git restore` away. Staging is fine; the commit is the user's.
- **kicad-review is the gate, and it is not negotiable.** Every authoring round ends with its ERC, DRC, firmware pin diff and checklists on the generated KiCad project. A finding is fixed in Zener or in the layout, or kept as a justified-ignore: a finding that is real but harmless by design (a deliberate GND-to-GND net tie, a test point the checker flags) stays in the report with the reason written next to it. Never edit the DRC rules, ERC settings or exclusions, and never drop a finding from the report, to make it clean.
- **Every electrical number has a source.** Pin numbers, absolute maximums, strapping levels, regulator equations, capacitor values: cite the fetched datasheet (URL and page) or the project's design note, in a comment next to the Zener that uses it. Datasheets and stock come through kicad-happy's `datasheets`, `lcsc` and `digikey` skills.
- **Nothing leaves the machine through Diode.** Never run `pcb auth`, `pcb publish` or `pcb quote`, never use build.diode.computer, never upload a design. `pcb bom` sends the part list to Diode's API: run it with `--offline` unless the user asks for live availability. Sourcing and the JLCPCB BOM, CPL and gerbers stay with kicad-happy and kicad-review step 7. Ordering and paying are human-only.
- **CLI facts come from `pcb help <command>`, not from memory or from this file.** The tool ships several releases a week, and the `pcb` shim auto-updates to the newest `pcbc` in the workspace's `pcb-version` lane (`major.minor`, `0.4`) on any call, `pcb --version` included. Accept the lane: write the toolchain version from `pcb --version` into every round report, and when it changed since the last round, read the changelog entries in between (`github.com/diodeinc/pcb/blob/main/CHANGELOG.md`) before relying on a flag. To repeat a round on an exact toolchain, `pcb +<version> <command>`. A lane change (`pcb-version`, `pcb migrate`) and installing or updating KiCad are the user's call.
- **Say what was not verified.** A board that builds and passes DRC has had no electrical validation, RF tuning, thermal check or bring-up. The report says so, and names what the user should look at in the KiCad GUI.

## Workflow

0. **Preconditions.** Confirm the session is on Fable. Run `pcb --version` and `pcb help`; missing `pcb` is a stop with the install command for the user, not something to install. Run kicad-review's `scripts/check_kicad.sh`. `kicad-cli` is not on `PATH` on this machine: `pcb layout` finds KiCad through `KICAD_CLI` and `KICAD_PCBNEW`, so check `pcb help layout` and set them to the app bundle's binaries if it cannot find KiCad. Read the repo's `## Hardware` section and the firmware pin header.
1. **Start the board.** New: `pcb new board <Name> <repo-url>` gives `<Name>.zen` and `pcb.toml` (the sources) and an `eda/` KiCad project (generated, but persistent). Existing KiCad project: read the import reference, then `pcb import <project>.kicad_pro .` in a new empty directory. Import rejects layout-only projects, files from a KiCad nightly and projects with more than one top-level sheet; `--force` only on an untouched starter.
2. **Parts.** Write the requirements and the part choices into the project's design note first, each with its datasheet. The stdlib has generics for passives, LEDs, crystals, headers, test points, TVS and mounting holes, and nothing for an ESP32-S3 module, a regulator or a USB connector. Those come from a registry package (`code.diode.computer`; if it asks for authentication, stop and take the other route) or from your own `Component()` on a `.kicad_sym` and `.kicad_mod`. Part identity is `Part(mpn=, manufacturer=)` or the symbol's properties. An LCSC number is not a Zener field: keep it in the project's `BOM.md`, where kicad-review reads it.
3. **Write the Zener.** Follow the language reference. Then `pcb sync` after a dependency change, `pcb fmt`, and `pcb build <Name>.zen` until the diagnostics are clean; `pcb fix` applies what the build reports as fixable, so read its diff. `pcb build` needs no KiCad.
4. **Layout.** `pcb layout --no-open <Name>.zen` creates the KiCad project or syncs an existing one, keeping placement, tracks and zones (`--sync-footprints` reloads footprint definitions and keeps placement and routing; `--no-sync` resolves the files without updating them). Diff the `.kicad_pcb` after the first sync on a board to confirm that. Place and route in this order: decoupling and other support parts against their pins; connectors where the enclosure and harness need them; then critical nets first (matched pairs, high current, noise-sensitive), with their return path under them; antenna keep-outs clear of copper and vias on every layer; the rest last. Rip up and redo a region rather than patch around a bad first attempt. The CLI has no router (`pcb route` does not exist in 0.4.99 or 0.4.100, though older changelogs mention one), so routing is your own scripted work, as in Anthropic's Fable 5.2 board work: point-to-point tracks you choose for the short and critical nets, and for the bulk a grid router of your own (A* on a grid at the track-plus-clearance pitch, per layer, with via cost; rip up and reroute the worst nets until nothing is left unrouted), then `pcb layout --check` and DRC. Keep helper scripts (the router, a clearance check) in the board repo under `tools/` and run them with `uv run`. Freerouting needs a Specctra DSN exported from the KiCad GUI (`kicad-cli` 10.0.5 has no DSN export), so it is a fallback only when the user exports one. Whatever is not placed or routed is reported as open, not as done: the user can finish it in the GUI.
5. **Check, every round.** `pcb layout --check <Name>.zen` (validates the layout without modifying it, then runs KiCad DRC), `pcb dfm --pdk <name> <Name>.zen` with the fab's PDK, and `pcb test` or `pcb sim` where a testbench exists. Then kicad-review steps 2 to 6 on the project in `eda/`: ERC, schematic checklist, pin diff against the firmware header, DRC, layout checklist. Run its `export_review.sh` and Read the PNGs: the picture is the only view of the board you get. Sort each tool finding into fix or justified-ignore, with the reason written down.
6. **Report.** What changed in Zener and in the layout, each check with its counts, the findings left open, what is unverified, and what to look at in KiCad. Fab outputs are kicad-review step 7, on the user's request.

## Orchestration

Authoring rounds are design iteration: the agent that writes the board also runs `pcb build`, `pcb layout` and the review exports and looks at the result. That is the main session when it is on Fable, a fork of it, or `general-purpose` launched with `model: "fable"` and `effort: "high"` (pass it on the call: a Fable subagent under a session on another model does not take the session's level, and Fable 5.2's Claude Code default is `medium`). `fast-executor`, `verifier`, `deep-reasoner` and `Explore` are on other models, so the hook denies their writes; `verifier` can still run the read-only checks (`pcb layout --check`, kicad-review's `erc_drc.sh`) at a milestone.
