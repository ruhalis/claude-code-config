# claude-code-config

Personal agent configuration for **Claude Code**, installed from one source of truth — plus the **VS Code** extension set.

```bash
git clone --recurse-submodules https://github.com/ruhalis/claude-code-config ~/projects/claude-code-config
cd ~/projects/claude-code-config
./install.sh
```

```bash
./install.sh                     # every tool detected on this machine
./install.sh claude              # one tool
./install.sh claude vscode       # several
./install.sh vscode              # merge VS Code settings, install missing extensions
./install.sh skills              # only the skills
./install.sh all                 # both, detected or not
./install.sh --dry-run all       # print the plan, change nothing
```

## Layout

```
core/                  source of truth: agents and skills
  agents/*.md            the specialists, in Claude's format
  skills/*/              SKILL.md skills
  skills/anatomy/        submodule: wheresryan22/anatomy, pinned (Claude Code only)
  skills/pcb-author/     the only write path for a board: Zener sources and Diode's pcb CLI, Fable only (Claude Code only; carries Diode's five skills as references, MIT, pinned in SKILL.md)
  skills/shopping/       read-only personal shopper for Kazakhstan: store reads (scripts/listing.py), landed cost in KZT, Artifact comparison pages (written for Claude Code: uses Agent and Artifact)
adapters/
  claude/                CLAUDE.md + settings.json + keybindings.json + hooks/ + mods/
  vscode/                extensions.txt — extension IDs to install; settings.json — user settings (merged)
scripts/               bench.sh, check-skills.sh, cleanup.sh
statusline/            submodule (Claude-only)
```

| Agents | `~/.claude/agents/*.md` |
| Skills | `~/.claude/skills/` |
| Settings | `settings.json` (merged copy) |
| Keybindings | `keybindings.json` (merged copy) |
| Statusline | `statusline/` (submodule) |
| Hooks | `~/.claude/hooks/guard-main-session.sh`, `~/.claude/hooks/guard-git-write.sh` and `~/.claude/hooks/guard-kicad-edit.sh` (symlinks to `adapters/claude/hooks/`) |
| clangd wrapper | `~/.local/bin/clangd` (symlink to `adapters/claude/bin/clangd`; `~/.local/bin` must come before `/usr/bin` on `PATH`; a clangd already at that path that is not this link is left alone with a warning). The `clangd-lsp` plugin starts the first `clangd` on `PATH` with a fixed command line, so the wrapper picks the binary by workspace: with an ESP-IDF project (`sdkconfig` or `sdkconfig.defaults` up to three levels down) it runs Espressif's clangd from `~/.espressif/tools/esp-clang` with `--query-driver` for the cross compilers and the system compilers; anywhere else, or without esp-clang, the system clangd unchanged. The project still needs a `.clangd` that removes the GCC-only `-f*`/`-m*` flags and one `idf.py build` for `build/compile_commands.json` |
| Subagent rows | `~/.claude/mods/agent-rows` (symlink to `adapters/claude/mods/agent-rows`): a mod whose `AgentRow` render hook makes the agent list show `type model effort · task · tokens` per running subagent, loaded through `CLAUDE_CODE_PLUGIN_DIRS` in the `env` of settings.json. It replaced the `subagentStatusLine` setting, which Claude Code deprecated in favour of mods; check it with `claude plugin validate` and `claude plugin test` on the folder |

Symlinked items track repo edits live. The two copies — `settings.json` and `keybindings.json` — are copies precisely because Claude Code rewrites `settings.json` in place when you change the theme or model, and a symlink would push those edits back into the repo. Re-run `install.sh` to update them: it backs up the live file, then merges the repo over it, so the repo wins on every key it declares and the live file keeps the rest, with `model`, `modelSettings`, `effortLevel` and `autoMode` staying as Claude Code last wrote them (the repo only seeds them when absent). A key removed from the repo is not removed from the live file because the merge never deletes, so remove it by hand or with `/config`. If `jq` is missing, or a live file cannot be merged (invalid JSON, or a top level that is not an object), `install.sh` stops before it changes anything; it never replaces a live file it could not merge.

### Engineering only: connectors, blocked skills, restored basics

Claude Code on this Mac is for engineering; the Claude app (Chat and Cowork) is the assistant for everything else. Three things keep the two apart:

- **claude.ai connectors are off in terminal sessions.** `~/.zshrc` (not managed by `install.sh`) exports `ENABLE_CLAUDEAI_MCP_SERVERS=false`, so Gmail, Google Calendar, Linear and Claude Docs do not load. Two shell functions there start a session with them on: `claude-all` (any folder) and `masters` (`~/projects/masters`, whose deadlines sync to Linear). Renee's `scripts/brief.sh` and the personal lane of `scripts/station.py` set the variable to `true` for their own `claude -p` runs. `disableClaudeAiConnectors` is not used: a `true` in any settings source wins everywhere, and it would cut Renee off. On a new machine, add the export and the two functions to the shell profile by hand.
- **Plugin connector servers are denied.** The `data`, `design` and `engineering` plugins declare 27 remote connector servers (Slack, Notion, GitHub, Snowflake and the rest) that would each try to connect at session start. `deniedMcpServers` in `settings.json` names every one as `plugin:<plugin>:<server>`; delete a line to use that connector.
- **Unused plugin skills are blocked, not hidden.** `skillOverrides` hides only personal skills (tested on 2.1.325: a plugin skill stays listed under either its full or its bare name), so the eleven plugin skills nobody here uses are denied with `Skill(...)` rules instead: cloudflare's `basin`, `k2`, `gateway-workers`, `cloudflare-one-migrations`, `sandbox-stable`, `sandbox-next` and `sandbox-migrate-to-next`; text-to-cad's `sendcutsend` and `pcb`; kicad-happy's `pcbway` and `kicad` (the `kicad-review` skill owns board review and calls kicad-happy's analyzers by path). They still appear in the skill list but cannot be loaded.

The basics that used to arrive through claude.ai sync are installed from their public marketplaces instead: `data`, `design`, `engineering` and `pdf-viewer` (`anthropics/knowledge-work-plugins`), `document-skills` for docx, pdf, pptx and xlsx (`anthropics/skills`), and `desktop-commander` and `skill-creator` (`claude-plugins-official`). desktop-commander's server is `npx @wonderwhy-er/desktop-commander@latest`, so it runs the newest npm release at each start; its two terminal tools and its four file-writing tools (`write_file`, `write_pdf`, `edit_block`, `move_file`) are denied, because neither guard hook sees them: a write through them would skip the Fable-only KiCad guard. The rest of its changing tools (`create_directory`, `set_config_value`, `kill_process`, `force_terminate`) are under `permissions.ask`, and so is Cloudflare's `execute`, which acts on the live account. The `cloudflare` marketplace is pinned to a commit like `rea`; move the `ref` in `settings.json` to update it. `deep-research` has no public source: `core/skills/deep-research/` is a local copy of the claude.ai skill as it was downloaded in October 2026, gitignored because it is Anthropic's to publish, so a fresh clone does not have it. The `docs` skill is not restored: it only points at the Claude Docs connector, which a `claude-all` session has.

## Skills

`core/skills/` is the only place skills are edited. The installed skill directory holds symlinks to it, so an edit is live the moment it's made. After adding or renaming a skill, `./install.sh skills` relinks just the skills (no settings copy) and names any skill still missing from `~/.claude/skills/`.

These skills are for Claude Code only. `settings.json` sets `syncClaudeAiSkills: false` and `syncClaudeAiPlugins: false`, so no skill or plugin from the claude.ai account loads into Claude Code, and nothing here is uploaded there: the Claude app (Chat and Cowork) keeps its own set. Old downloads from before the switch may still sit in `~/.claude/skills/.trash/` and `~/.claude/plugins/.trash/`; Claude Code does not load them.

```bash
scripts/check-skills.sh                # lint every skill; exit 1 on any FAIL
scripts/bench.sh                       # does the installed setup behave as claimed; --live adds claude -p runs
```

`core/skills/anatomy` is the exception: a submodule pinned to an upstream commit (40 MB, needs Node 20.10+ and Chrome), so it is Claude Code only. Don't edit it in place; update it with `git -C core/skills/anatomy fetch && git -C core/skills/anatomy checkout <commit>`, then commit the new pin.

- `check-skills.sh` needs only bash and python3. It fails a skill whose frontmatter breaks the Agent Skills spec (a key outside `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`; `name` not the directory name; `description` over 1024 characters; `compatibility` over 500; a non-string `metadata` value), a script that does not parse or whose `--help` breaks, a bundled path `SKILL.md` names that does not exist, or a missing version-pin file. It warns about `__pycache__` and `.DS_Store`. Last it checks every `~/.claude/skills/<name>/<path>` reference in the Markdown under `~/projects`, because other repos call the bundled scripts by those paths. The header of the script lists every rule.
- `install.sh` runs `check-skills.sh` after any install that links skills. It only reports.
- `bench.sh` checks that the install matches this README: every symlink points into the repo, the live settings carry the guard hook, the deny list, the cache TTL and the subagent env, the agent frontmatter pins the documented models and effort, and the guard hook decides correctly on synthetic input. `--live` adds nine headless `claude -p` sessions (API cost, a few minutes) in a throwaway repo whose CLAUDE.md holds a sentinel word: the main session and a general-purpose subagent must know it, Explore must not, the guard hook must deny `pytest` in the main session and allow it in a subagent, `git clean -fd` must stay blocked under `bypassPermissions`, and `modelUsage` must show haiku for Explore, sonnet for general-purpose and fast-executor, and opus for deep-reasoner. `--keep` leaves the transcripts and the hook-input log for inspection. Run it after an install or a settings change.

### What the skills read from a project

The skills hold workflow and boundaries; project facts live in the project, in `CLAUDE.md` (or `CLAUDE.local.md`) sections with one greppable `key: value` per line. A skill that finds its section missing works the facts out, then offers to write the section.

| Section | Read by | Keys |
|---|---|---|
| `## Boards` | esp-idf | `<board name>: <serial port>` |
| `## Hardware` | kicad-review, pcb-author, pcb-enclosure | `kicad:`, `pins:` (the firmware pin header), `mcu:`, `fab:`, `note:` |
| `## Print` (optional) | pcb-enclosure | `printer:`, `nozzle:`, `material:`; absent means 0.4 mm nozzle, PLA or PETG |
| `## Motors` | motor-bench | `rule:`, `rig:`, `program:`, `send:`, `probe:`, `moves:`, `stop:`, `user-only:`, `kill:`, `limits:`, `watchdog:`, `supply:`, `direction:`, `log:` |
| `## Experiments` | rl-advisor | `log:`, `run-id:`, `runs:`, `metric:`, `eval:`, `framework:` |

Keep this order, `## Boards` first and short: esp-idf reads a fixed 12 lines after its heading, and motor-bench reads up to the next heading. The sections also connect skills: when firmware changes the header `## Hardware` names as `pins:`, esp-idf hands back to kicad-review's pin diff, and a flash or reset of a board wired to ESCs or drivers follows motor-bench as well as esp-idf. led-animation reads the free-form `CLAUDE.md` section on the renderer and the host tooling's README instead; isaac reads the pin from `CLAUDE.md`, `.gitmodules` and `STATUS.md`. rl-advisor answers the RL theory and design questions around a run and keeps its record (in aquila the ledger row and its EVIDENCE §9 row, elsewhere an entry in the template of `references/isaac-lab-log.md`); its `references/aquila-map.md` digests only the durable facts of aquila (structure, locked hyperparameters, method, closed results with their EVIDENCE section); the moving state (shipped student, open decisions, pending verdicts) stays in `verro/STATUS.md` and `verro/EVIDENCE.md` and the digest points at it by row ID, so refresh the digest only when a lever is kept or a campaign closes, not per run.

## VS Code settings and extensions

`adapters/vscode/settings.json` holds the VS Code user settings this repo cares about (today: `workbench.secondarySideBar.defaultVisibility: hidden`, so the Chat / Claude Code side bar starts closed). `./install.sh vscode` merges it into `~/Library/Application Support/Code/User/settings.json` (`~/.config/Code/User/` on Linux) the way the Claude settings are merged: the repo wins on the keys it declares, every other live key stays, the old file goes to the backup folder, and on a fresh machine the file is simply copied. Keep the repo file plain JSON, with no comments: the merge runs through `jq`. A live file that `jq` can't parse (VS Code accepts comments and trailing commas), a symlinked one, or a live file on a machine without `jq` is left alone with a warning, never replaced. This step doesn't need the `code` CLI. Toolbar buttons hidden with a right-click are kept in VS Code's internal state database rather than `settings.json`, so they don't carry over.

`adapters/vscode/extensions.txt` lists extension IDs, one per line, `#` comments allowed. `./install.sh vscode` — or a bare `./install.sh` when VS Code is detected — installs whichever are missing in a single `code --install-extension` call, always at the latest marketplace version; nothing is pinned. Extensions already on the machine are never removed, including ones the list doesn't mention. Those are reported instead, so you can add them:

```
installed here but not in extensions.txt: publisher.name
```

To capture what you've installed since, append the new IDs from `code --list-extensions` to the file. The installer needs the `code` CLI: it looks on `PATH` first, then inside the macOS app bundle. If neither is found it warns and skips — run **Shell Command: Install 'code' command in PATH** from the Command Palette and re-run.

## Backups and safety

Anything pre-existing is backed up to `~/.agent-config-backups/<timestamp>/<tool>/`, never deleted.

**Swept** — `~/.claude/agents/` and `~/.claude/skills/` are owned by this repo. Anything not from here is backed up and removed, so after install they mirror the repo exactly. The exceptions are `~/.claude/skills/synced/` (skills Claude Code downloads from claude.ai) and `~/.claude/skills/.trash/`, which belong to Claude Code and are left alone.

Each `link` line says `new`, `exists` (already that link) or `replace`, so `--dry-run` shows what a run would change.

## Cleaning developer caches

`scripts/cleanup.sh` is opt-in and not run by `install.sh`. With no flags it only reports cache sizes. `--purge` clears the safe caches (brew, npm, uv, Xcode DerivedData, unavailable simulators). `--purge-heavy` also offers Docker images and model weights, each behind a y/N prompt unless `--yes` is given. Add `--dry-run` to print what would run.

## Agents & orchestration

`adapters/claude/CLAUDE.md` makes the main agent an orchestrator that delegates what would flood its context or can run in parallel, and keeps the rest: understanding the request, planning and design decisions, the edits whose shape is still open, reading agent reports, integrating and reporting. The rule states the price of a subagent first (a fresh context, and only a summary back), following Anthropic's Fable 5.2 prompting guide, where a cost-first delegation rule cut delegation by about a third at the same task success. Work that would return more than a screen of output or sweep many files goes to an agent before it starts; a lookup with a known target, the one document a decision rests on, and a short-output step of up to about five tool calls stay in the main session. Tests, builds, validation batches, benchmarks, smoke tests and checksum reruns are never run in the main session. On a Fable main session, plans and design decisions stay there too, and deep-reasoner gathers the evidence. Fable 5.2 and Opus 5.5 run at `xhigh` (`modelSettings`). Two side effects come with that level: at `xhigh` and `max` Fable 5.2 starts subagents to review its own work, on top of the delegation here, and a subagent on Opus or Fable that has no `effort` of its own takes the saved level, which is why the agents below pin theirs. The section also splits work by context rather than by role, and keeps workflows to one per request once the user opts in. It routes to specialists, each with a pinned model so nothing inherits the session model (`CLAUDE_CODE_SUBAGENT_MODEL=sonnet` covers `general-purpose`; the built-in `Plan` ignores that variable and inherits the session model):

- **deep-reasoner** (Opus at xhigh, read-only) — any investigation that spans several files or runs, and complex debugging. On an Opus or Sonnet main session it also makes the hard design decisions, plans for large or risky changes and algorithm choices; on a Fable main session those stay with the orchestrator and deep-reasoner gathers the evidence.
- **fast-executor** (Sonnet at medium) — boilerplate, patterned edits across separate files, fixes whose shape is already decided, tests; it runs the targeted test for what it touched.
- **implementer** (Opus at high) — a specified part that still needs judgment: a module, a feature slice or a diagnosed fix with its own files, a spec and a check. It makes the local design choices, writes and runs the targeted tests and reports what it decided. It replaces `general-purpose` with a model override for this work, which ran at whatever effort was saved for that model.
- **verifier** (Sonnet at medium, read-only) — runs every test suite, build, batch and smoke test on the orchestrator's behalf and returns pass/fail with the decisive lines; at milestones, after long unattended work or on high-stakes changes it also checks the integrated result against the acceptance criteria.
- **Explore** (Haiku at low, read-only) — broad fan-out searches; returns `file:line` locations, overrides the built-in Explore agent.

The rule is enforced, not only stated: `adapters/claude/hooks/guard-main-session.sh` is a `PreToolUse` hook on `Bash` (wired in `settings.json` with `onFailure: block`) that denies test and build commands in the main session (`pytest`, `npm test`, `cargo test`/`build`, `go test`, `ctest`, `ninja`, `make test`/`check`/`all`, `cmake --build`, and `idf.py` build-type actions such as `build`, `app`, `bootloader` and `size` whatever options come first, so `idf.py -C "<dir>" build` is caught) and names the verifier in the denial. The runner is matched as a word anywhere in the command, so a path prefix (`.venv/bin/pytest`), a separator right after it (`pytest; echo done`, `idf.py build|tail`), arguments (`npm test -- --watch`) and a subshell (`x=$(pytest)`) are all caught; segments whose command only names or reads things (`grep pytest`, `which pytest`, `uv add --dev pytest`, `git log --grep pytest`) are dropped before matching, so they pass. Flash, monitor and menuconfig stay allowed. The hook ignores heredoc bodies and quoted strings when matching, so a commit message or note that mentions `pytest` passes; a test command hidden inside quotes (e.g. `bash -c "pytest"`) is not caught, which is acceptable since the guard backs up an instruction rather than resisting an adversary. Calls from subagents carry `agent_id` in the hook input and pass through. `GUARD_MAIN_SESSION_OFF=1` in settings `env` disables it. Without jq the hook fails closed: it exits 1, so `onFailure: block` stops the call. `settings.json` also carries a `permissions.deny` list (`git commit` and `git push`, also with `-C <dir>` when arguments follow; `gh pr create`; `git merge`, `rebase`, `cherry-pick`, `revert` and `tag` in their plain form, which also blocks listing tags, so read them with `git for-each-ref refs/tags`; the sweeping `git add` forms `-A`, `--all`, `-u`, `--update` and `.`; force pushes in any flag order, `git reset --hard`, `git clean -f`, `rm -rf` of `~` or `/`, and desktop-commander's two terminal tools, which the Bash-only hook can't see) that applies in every permission mode and to subagents. These rules cover the forms Claude usually writes, not every spelling: `git -c k=v commit`, a bare `git -C <dir> push` and the other verbs behind `-C` are not matched and rest on the `# Git` rule in CLAUDE.md. A `permissions.ask` rule (`mcp__plugin_rea_rea__*`) makes every rea MCP tool call prompt, in auto mode too. `settings.json` also sets `subagentPromptCacheTtl: "1h"` so long fan-outs keep their prompt cache, and `maxTurns` on fast-executor (60), implementer (100) and verifier (80) so a runaway run returns partial, resumable output.

`adapters/claude/hooks/guard-git-write.sh` (`PreToolUse` on `Bash`, `onFailure: block`, every agent) backs the never-commit rule. The `permissions.deny` patterns match the command text, so `git -C dir commit` or `git -c k=v push` slip past them; the hook finds the real subcommand behind git's global options, env prefixes, wrappers, chains, `$(...)` and `bash -c`, and denies `commit`, `push`, `merge`, `rebase`, `cherry-pick`, `revert`, `tag`, the sweeping `git add` forms and `gh pr create`. It does not see git aliases, `eval`, or history writers the rule doesn't name (`pull`, `am`, `update-ref`).

A third hook, `adapters/claude/hooks/guard-kicad-edit.sh` (`PreToolUse` on `Edit|Write|Bash|mcp__.*[Kk][Ii][Cc][Aa][Dd].*`, also `onFailure: block`), lets only Claude Fable 5.2 or later change a board. It guards `Edit` and `Write` on `*.kicad_sch`, `*.kicad_pcb`, `*.kicad_pro`, `*.kicad_sym`, `*.kicad_mod`, `*.kicad_wks`, `*.kicad_dru` and `*.zen`; shell redirects, `tee` and `sed -i`/`perl -i` into those files; the writing subcommands of Diode's `pcb` CLI (`layout`, `import`, `apply`, `new`, `fmt`, `fix`, `migrate`, `route`, `embed-step`, unless the segment carries `--check`); `pcb-component-gen`; `kicad-cli <sch|pcb|sym|fp> upgrade`; kicad-happy's two `bom` scripts that rewrite symbol properties in a schematic (`edit_properties.py` and `sync_datasheet_urls.py`, unless the segment carries `--dry-run` or `--help` or only reads the script); text-to-cad's board edit API (`kicad_pcb.edit` / `kicad_sch.edit`, inline or in any existing `*.py` the command names, as in `cad run board.py`); and the writing tools of a KiCad MCP server (by verb in the tool name). text-to-cad's own `pcb` skill is also denied for every model by `Skill(text-to-cad:pcb)` in `permissions.deny`, because it saves boards in KiCad's nightly format. The hook input has no model field, so the hook reads the model from the transcript: the last assistant message of the session file, or of `<session>/subagents/agent-<agent_id>.jsonl` for a subagent. Two consequences follow from reading the previous message rather than the one issuing the call: a subagent's very first tool call has no model on record and is denied, and the first call after `/model` is judged by the old model. Anything other than Fable 5.2 or later (`claude-fable-5-2` and up; Fable 5.1 scored below Opus 5.5 on BenchCAD 2.1), including an unknown model, is denied with a reason that names the `pcb-author` skill and how to hand the edit to Fable. It is best effort on `Bash` (a script that writes the files itself is not seen), and `GUARD_KICAD_OFF=1` in settings `env` disables it. The write path is the `pcb-author` skill; `kicad-review` stays read-only and gates what `pcb-author` produces. Diode's `pcb` CLI is not installed by `install.sh`: run its installer yourself (`~/.local/bin/pcb`).

Delegation is mandatory for validation because batch output is noise in the main thread: a session that runs its own batches buries the task under it and loses the thread, and that costs more than the extra tokens the agents spend. The specialists have no `Skill` tool: esp-idf hands them a restricted prompt block instead, and hardware actions (flashing, resets, motors) stay with the main session.

`settings.json` also turns on Claude Code's advisor tool with `advisorModel: fable`. The orchestrator consults it before committing to the plan for a large or risky change, when an error keeps recurring, and before reporting a milestone done. The advisor reads only the transcript, so an investigation that needs files still goes to deep-reasoner and pass/fail still comes from verifier. Subagents inherit it, billed as Fable usage, and each call re-reads the caller's whole transcript uncached, so among subagents only deep-reasoner consults it: CLAUDE.md tells every other subagent not to, Explore, verifier, fast-executor and implementer carry the line in their own prompts, and every `general-purpose` brief repeats it. A Fable 5.2 main session accepts only Fable 5.2 as its advisor (Claude Code 2.1.321 or later), which is why the setting is `fable`: with `opus` a Fable session starts with no advisor and says so at launch. `/advisor` writes to the home settings copy, which the next install overwrites.
